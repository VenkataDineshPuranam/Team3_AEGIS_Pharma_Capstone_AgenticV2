# Prompt 06 — C4 Architecture (Design — Structure)

**Lifecycle stage:** Design (system) / Spec-Driven Development — Architecture  
**Framework derived:** C4 model (Context, Containers, Components, Code)  
**Core question:** What does the system look like?  
**Prerequisites:** Prompt 04 DDD; Prompt 05 feature index (in-scope behaviors).  
**Primary output type:** Architecture views (the “map”; may be provisional).

---

## Intent

Derive the **C4 framework**: show structure that realizes the domain model and hosts the feature set. C4 answers **what** the system looks like. The **why** is deferred to Prompt 07 (ADR). Technical contracts come in Prompt 08.

Reference line: *C4 is the architecture map. ADR is the decision memory behind the map.*

If Prompt 04 artifact status is `provisional`, mark C4 outputs **provisional**, keep the map to the minimum governed workflow, and avoid elaborate multi-agent topologies until evidence improves.

---

## Entry criteria

- Bounded contexts, minimum governed workflow, and rules/AI/HITL boundaries exist.
- Feature index exists (which capabilities the architecture must support).
- DDD artifact status (`stable` | `provisional`) is known.
- Prohibited behaviors from domain (e.g. unauthorized write-back) are known.

---

## Produce

**Artifact status (required):** `stable` | `provisional` (inherit `provisional` from Prompt 04 unless new evidence justifies upgrade — document it).

### C4 levels

1. **Level 1 — System Context** — people/roles and external systems interacting with the solution.
2. **Level 2 — Containers** — independently deployable or runnable units (apps, data stores, brokers, services, agent runtimes, etc.).
3. **Level 3 — Components** — critical decision-workflow modules inside each container (include rule engines, retrieval, agents, HITL interfaces where relevant).
4. **Level 4 — Code** (where warranted) — key classes, interfaces, or modules for the riskiest paths.

### Cross-cutting views (required)

- **Mapping** — each major architecture element ↔ bounded context from Prompt 04; note which features (FR-IDs) land in which container/component.
- **Boundaries** — data, trust, privacy, authority, and connectivity across levels.
- **Degraded / offline mode** — behavior when connectivity or dependencies fail.
- **Prohibited operational write paths** — what must never be written back or mutated.
- **Gen AI runtime sketch** — where retrieval, model calls, tools, and human review sit in the container/component view (structure only; justify choices in ADRs).
- **Agentic runtime view (V2, required):** show the orchestration container (LangGraph graph: nodes = agents, edges = handoffs/state transitions, explicit HITL interrupt points), the MCP tool-server containers each agent may call, the cache container (Redis — semantic + exact-match), and the observability container (LangSmith/OTel trace sink). This becomes the primary input to Stage 10 (`docs/architecture/agentic/`) and Stage 11 (`services/integration/`, `.claude/mcp.json`).

### Decision candidates (for Prompt 07)

List architecture choices that need ADRs (options visible, decision not finalized here unless already constrained by evidence).

### Lean / DMAIC lens (spine — FULL at this stage)

**DMAIC focus this stage:** run the **full** Define → Measure → Analyze → Improve → Control cycle, building on Prompts 01/02/04's registers — do not restart from a blank page. C4 is a designated full-DMAIC stage (with Discovery/01, Frame/02, DDD/04, ADR/07).

In `dmaic_lens.md`, record the full cycle:

1. **Define** — restate the improvement problem at architecture granularity: which container/component boundary exists specifically to eliminate a named waste?
2. **Measure** — which architectural metrics (hop count, sync-call depth, fan-out) are measurable proxies for Transportation/Waiting waste, and what are their current/target values?
3. **Analyze** — does the map reduce Transportation / Integration waste (fewer hops, clear SoT)? Where could containers create Waiting (sync chains, human-review bottlenecks)? Risks of Observability waste (logs/metrics with no owner) or Context waste (reconstructing state everywhere)? Any over-built containers that look like Overproduction vs minimum governed workflow?
4. **Improve** — the architecture itself is the Improve artifact: state explicitly, per container, which waste it removes and which trade-off it accepts (point to the ADR).
5. **Control** — which container/component needs a health/SLO check so architectural drift or degraded mode is caught operationally, not just documented (feeds `boundary_and_degraded_mode.md`).

Update, do not restart:

- **DOWNTIME waste register** (`waste_register_downtime.md`) — carried from Prompts 01/02/04, refined with architecture-level findings.
- **AI-specific waste register** (`waste_register_ai_specific.md`) — same, with particular attention to Integration/Observability/Context waste since those are architecture-visible.
